# Вывод в интернет и безопасность

Пока шлюз и дальний телефон в одной Wi-Fi — всё работает «как есть». Чтобы звонки и SMS
доходили **из любой точки**, шлюз должен быть доступен из интернета. Телефон-шлюз стоит за
роутером, у роутера — **белый (публичный, без CGNAT) IP**. Твой телефон с софтфоном — где угодно.

> ⚠ **Эта часть написана, но ещё не проверена вживую** (на момент 22.10.2026 — только LAN).
> Проверяется при переезде телефона на локацию с белым IP.

## Вариант 1 (рекомендуемый): VPN вместо пробросов

> ⚠ **Статус проверки: в теории работает, на практике ещё не гоняли.** Tailscale или любой другой
> VPN, объединяющий телефоны в общую overlay-сеть, по логике подходит, но сквозной тест
> (регистрация + звонок + SMS поверх VPN) мы пока не делали. Проверка запланирована — все телефоны
> проекта сейчас доступны по adb, так что это реально проверить.

**Лучшее решение — не светить SIP наружу, а поднять VPN** (WireGuard) между локацией шлюза и
твоим телефоном. Тогда:

- **пробросы портов не нужны вовсе** — оба конца в одной VPN-подсети, всё как в LAN;
- **STUN можно держать выключенным** (анонсируется VPN-адрес шлюза);
- `5062`/RTP слушаются только на VPN-интерфейсе — снаружи порт не виден;
- снимается и проблема безопасности, и возня с NAT/SDP.

Схема: WireGuard-сервер на роутере локации шлюза (или на отдельном узле), телефон-шлюз и
дальний телефон — клиенты в одной VPN-подсети. Софтфон регистрируется на VPN-адрес шлюза.

## Вариант 2: проброс портов на роутере

### 1. Стабилизировать адрес шлюза в LAN

На роутере включить **DHCP-резервацию** для MAC Wi-Fi телефона-шлюза, чтобы его локальный IP не
менялся — на него смотрят пробросы.

### 2. Пробросить порты (UDP)

| Внешний порт | → Внутренний (телефон-шлюз) | Что |
|---|---|---|
| UDP **5062** | `<LAN IP шлюза>:5062` | SIP: REGISTER, INVITE, ACK, BYE, MESSAGE |
| UDP **30000–40000** | `<LAN IP шлюза>:30000–40000` | RTP (звук). **1:1, те же номера портов** |

> ⚠ RTP пробрасывать **без трансляции номеров** (внешний порт = внутренний). Шлюз указывает в
> SDP конкретный выбранный RTP-порт из диапазона; если роутер его переназначит, звук уйдёт не
> туда — ровно тот баг с «мёртвым портом», только снаружи.

### 3. Включить STUN в приложении

Настройки шлюза → **STUN включить** (`use_stun=true`). Приложение подставит в Via/Contact/SDP
**публичный IP** вместо локального. В журнале при старте должно быть:
`STUN public IP: <твой белый IP>:<порт>`. Если там `STUN off — advertising 192.168.…` — STUN
выключен, снаружи ничего не соединится.

> Порт в Contact остаётся **5062** (`advertisedPort`), совпадает с пробросом; STUN берётся
> только для IP. Если STUN определит IP неверно (сложный NAT) — это слабое место: поля
> «анонсировать вручную такой-то IP/домен» в приложении пока нет (кандидат в доработку).

### 4. Клиент

Нацелить софтфон на `<белый IP>:5062` (см. [`client-baresip.md`](client-baresip.md)). Если есть
домашний домен/DDNS — лучше по домену: переезд/смена IP тогда не ломает клиента.

## ⛔ Безопасность — обязательно прочитать

В режиме встроенного регистратора **аутентификации нет** (пароль пустой). Открыв `5062` в
интернет «как есть», ты пускаешь кого угодно:

- любой, кто найдёт порт, может **зарегистрироваться как «100»** и перехватывать входящие
  звонки (шлюз звонит первой живой регистрации);
- можно заставить шлюз **звонить/слать по GSM наружу** — это реальные деньги (toll fraud);
- SIP-сканеры постоянно щупают интернет, нестандартный `5062` найдут за часы.

Что делать (по убыванию надёжности):

1. **VPN (вариант 1)** — лучший вариант, снимает проблему целиком. Рекомендуется.
2. Если всё-таки проброс — на роутере **ограничить источник**: разрешить UDP 5062/RTP только с
   IP твоего телефона/оператора (firewall-правило «allow from `<IP клиента>`, deny остальное»).
   Работает, если IP клиента более-менее статичен.
3. Нестандартный порт `5062` чуть снижает фон сканеров, но сам по себе не защита.
4. Следить за журналом: чужой `Registrar: …` с незнакомого IP — тревога.

> Правильная защита — **SIP-аутентификация** в режиме регистратора (проверка пароля на
> REGISTER/INVITE/MESSAGE). Сейчас её нет — это осознанный TODO. До неё: **VPN или allow-list
> по IP**. Не выставляй `5062` в открытый интернет без одного из этих ограничений.
